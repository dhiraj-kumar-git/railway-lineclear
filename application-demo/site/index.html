Field staff: report a problem on the line

A track inspector or loco pilot reports what they see. This is a public call (POST /api/incidents), no staff key. If the report names a train, the duty controller diverts it through the loop line, and that diversion is a two-phase commit.

Ready-made scenarios

Each button sends real reports. Free the track (control office) between scenarios.

Scenario C, the duty controller freezing mid-commit, starts from the control office: arm the fault switch there, then run scenario A.

Control office: the station master's console

Reads the four public APIs every few seconds. Staff actions (resolve, fault switch, free the track) go through this laptop's control-office server, which adds the staff key from Secrets Manager; the key never reaches the browser.

Duty controller f

Two Schedule Manager replicas compete for one 6-second lease in Leader Election. The holder coordinates every diversion; its term is the shift number, and orders from an older term are refused.

    Staff actions

    Checking the staff key

    Arms the fault switch for 20 s (POST /api/schedule/fault-switch). Then run scenario A: the leader logs COMMIT and freezes, the other replica takes over with a higher term, reads the log and finishes the job.

    Releases every loop-line hold (gRPC TrackStatus.ReleaseAllHolds) and resolves open incidents, so the next scenario starts clean.

    Trains and scaling
    
          
    Trains send GPS reports to Position Ingestion (POST /api/positions), which checks the train with Train Registry, keeps the latest position in DynamoDB and streams every report to Kafka for Flink. These two services carry the most traffic, so each has a Horizontal Pod Autoscaler: 60% CPU target, 2 to 8 pods. c
